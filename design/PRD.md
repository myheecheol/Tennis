## 1. 한 장 요약

**문제** — 구력 1년 미만 동호인은 스트로크는 되는데 복식만 서면 얼어붙는다. 어디 서야 할지, 공을 어디로 보낼지 아무도 안 가르쳐준다.

**해결** — 코트 그림 위에서 "지금 나는 어디로?" "이 공은 어디로?"를 손가락으로 찍고, 정답과 이유를 즉시 받는다. 상황 카드 120장.

**대상** — 40대 직장인, 구력 8개월, 주말 동호회 복식. 하루 6분, 지하철에서.

**차별점** — 유튜브는 남의 경기라 내 시점이 아니다. 이 앱은 **전부 1인칭**이고, 정답이 하나가 아니라 **정답 / 차선 / 실수** 3단계다.

**성공의 정의** — 앱 점수가 아니라 코트 위 행동 변화. 4주 사용자의 40%가 "이번 주 미션을 세 번 이상 실행했다"고 답하는 것.

## 2. 문제 정의

### 관찰된 사실

- 동호회 복식에서 초보자는 **자기 자리를 몰라 두리번거린다.** 특히 넷맨일 때 사이드라인에 붙어 서 있다
- 리턴을 무조건 세게 치려다 상대 넷맨에게 잡힌다
- 로브가 머리 위를 넘어가면 **제자리에서 공을 눈으로 쫓는다.** 스위치를 모른다
- 가운데 뜬 공을 둘이 서로 쳐다보다 놓친다

### 기존 대안이 왜 부족한가

| 대안 | 문제 |
|---|---|
| 유튜브 | 남의 경기 3인칭. "저 상황에서 내가 저 자리면?"이 안 떠오른다 |
| 레슨 | 대부분 스트로크 교정. 복식 전술은 다루지 않거나 말로만 한다 |
| 책 | 정적인 그림 + 텍스트. 판단을 연습할 수 없다 |
| 동호회 선배 | 조언이 사람마다 다르고, 조건 없이 단정한다 ("무조건 크로스") |

**공통점: 어느 것도 "판단"을 연습시키지 않는다.** 읽고 보기만 한다.

### 이 제품이 없으면

복식 전술은 **몇 년간 코트에서 혼나면서** 배우게 된다. 그 과정에서 많은 사람이 복식을 재미없어하고, 일부는 그만둔다.

## 4. 제품 정의

### 코어 루프 (30초)
상황 속 공이 날아와 **결정하는 순간에 멈춘다** → 단서 한 줄 → 질문 + 존 세 곳 → 탭 →
**고른 대로 공과 사람이 움직인다 → 성공 · 아쉬움 · 실패** → 해설 → **한 줄 요약** → 다음

정답을 "알려 주는" 대신 **내 선택의 결과를 보여 준다.** 실수를 고르면 넷맨에게 잡히는 장면을, 정답을 고르면 포인트를 따는 장면을 본다.
틀렸으면 `정답 장면 보기` 로 같은 판에서 정답의 결과를 바로 비교한다.

`한 줄 요약` 뒤에 **다음 수(`next`)** 를 붙여 카드가 랠리로 이어지게 한다. 이것이 "한 판 더"의 엔진.

### 모드

| 모드 | Phase | 규칙 | 시간 |
|---|---|---|---|
| 오늘의 코트 | 1 | 새 5 + 복습 3 (무료 3+2) | 6분 |
| 오답 노트 | 2 | 간격 반복. 실수 1→3→7→21일, 차선 3→14일 | 3분 |
| 10초 룰 | 2 | 카드당 10초. 점수 안 깎음 | 4분 |
| **두 수 앞** | **2** | 카드 2장 연쇄. 첫 선택이 둘째 카드를 정한다. 카드에 이미 있는 `next.id` 만 쓰므로 **추가 데이터 0** | 2분 |
| 한 포인트 | 3 | 5수 연속 + 분기 (`branch` 스키마 필요) | 5분 |

> **`두 수 앞` 을 Phase 2에 넣은 이유** — STEP 7 검수에서 "선택이 결과를 바꾸지 않으면 퀴즈지 게임이 아니다"는
> 지적을 받았습니다. 분기표 없이 두 수만 이어도 "내 선택이 다음 상황을 만든다"는 감각은 전달됩니다.

### 채점

| 선택 | 점수 | 경험치 | 오답 노트 | 결과 장면 | 화면 |
|---|---|---|---|---|---|
| 정답 | 100 | +10 | — | 포인트를 딴다, 또는 우리가 주도권을 쥔 채 이어진다 | `✓ 성공` 초록 |
| 차선 | 60 | +4 | 14일 뒤 | 랠리가 이어진다 | `△ 아쉬움` 호박 — **"나쁘지 않습니다. 그런데 —"** |
| 실수 | 0 | 0 | 1일 뒤 | 포인트를 잃는다 | `✕ 실패` 붉은색 |

결과 장면이 채점과 거꾸로면(실수인데 포인트를 딴다) 배운 게 뒤집힌다. **검증기가 장면을 끝까지 따라가 채점과 맞는지 본다.**

**연속 정답 보너스는 넣지 않는다.** 압박을 만들면 어려운 카드를 피하게 된다.

### 성장 — 동호인 부수

`신인부 → 5부 → 4부 → 3부 → 2부 → 1부`. 앱 안에서는 **"전술 부수"** 로 표기해 실제 동호회 부수와 구분한다. 역할별(서버·넷맨·리시버·리시버 파트너) 숙련도는 상세 화면에만.

### 난이도 적응

목표 정답률 **70~80%**. 3장 연속 실수 → 선행 카드를 끼워넣는다. 최근 10장 60% 미만 → 새 카드 비율을 낮춘다. **보기는 항상 3개**(2개면 찍어서 맞는다), **제한 시간은 10초 룰에만.**

### 화면 목록

| 화면 | 한 줄 목적 |
|---|---|
| 홈 | 오늘 할 것 하나 + 전술 부수 |
| 카드 | 코트 + 질문 + 보기 3개 |
| 해설 | 정답 존·화살표·이유·한 줄 요약·다음 수 |
| 챕터 | 진도와 잠금 상태 |
| 오답 노트 | 재출제 대기 목록 |
| 이번 주 미션 | 한 줄 규칙 + 주말 후 응답 |
| 통계 | 역할별 숙련도, 정답률 추이 |
| 설정·구독 | |

## 5. 콘텐츠 설계

### 구조

| 챕터 | 제목 | 목표 | 장수 | 난이도 |
|---|---|---|---|---|
| C1 🔓 | 네 자리를 안다 | 네 역할의 시작 위치, 파트너와 한 덩어리로 | 24 | 1~3 |
| C2 | 첫 세 번의 공 | 공의 높이로 전진·후퇴를 정한다 | 24 | 2~4 |
| C3 | 네트를 잡는다 | 둘이 함께 올라가고 유지한다 | 24 | 2~4 |
| C4 | 밀릴 때 | 무리하지 않고 로브로 리셋 | 24 | 2~5 |
| C5 | 상대를 읽는다 | 대형별 공략, 두세 수 앞 | 24 | 3~5 |

질문 유형 분포: `move` 43% · `target` 30% · `both` 13% · `readNext` 14%.
C1은 위치 중심(58%), C5는 판단 중심(`both`+`readNext` 50%)으로 무게가 이동한다.

### 카드 스키마

`data/cards/*.json`. 전체 스키마와 예시는 `reference/card-exemplars.md` 참조.

```
id · chapter · title · difficulty · prereq · myRole · phase · view(선택: me)
setup { me · partner · opp1 · opp2 }          ← zone + 정규 좌표
setup.ball { kind · arc · from · bounce · to } ← 3D 궤적과 깊이 태그의 원천
scene · cue · question{type, text}
answer { zone · short · why · principle · reveal(readNext) }
distractors[2] { zone · severity(차선|실수) · short · why }
  └ 보기마다 결과 장면 { stand? · moves? · caption · play[1~4] { by · arc · bounce · to · winner · call } }
coachLine · next{id, text} · tags
```

**글자 수 한도** — 제목 20 · 상황 38 · 단서 26 · 질문 14 · 보기 14 · 해설 **56(한 문장)** · 한 줄 요약 24 · 결과 한 줄 12.
검증기가 넘치는 카드를 거부한다.

### 제작 파이프라인

```
prompts/02 로 8장 생성  →  tools/validate_cards.py (기계 검증)
     →  사람 검토(전술)  →  tools/check_consistency.py (인덱스 대조)
     →  data/cards/*.json 커밋  →  앱 번들에 동봉
```

**검증기가 잡는 것** — 서브 대각선 위반, 서버·넷맨 반쪽 위반, 존 밖 좌표, 마커 겹침, 정답=오답 중복, 차선/실수 구성, 유형별 정답 코트, 정답 존 편중, **결과 장면과 채점의 불일치**.
실제로 이 검증에서 **예시 카드의 좌우 뒤집힘**이 잡혔다. 사람 눈으로는 못 잡는 종류다.

**검증기가 못 잡는 것** — 전술이 실제로 맞는가. **코치 감수 필수.**

## 6. 시각 설계

**내가 아래, 상대가 위** — 카메라는 뒤집지 않는다. 코트와 공은 **3D**로 그린다.

| 시점 | 카메라 | 언제 |
|---|---|---|
| **중계** (기본) | 우리 뒤 높은 곳, 망원 — TV 중계 화면 | 배치·간격·대형을 볼 때 |
| **내 시점** | 내 등 뒤 4.2m · 높이 3.4m | 네트 근처에서 상대를 볼 때 (25장 중 5장이 기본) |

**공이 길게 오는지 짧게 오는지**가 이 화면의 핵심이다. 실제 포물선 리본 + 바닥 그림자 + 바운드 링 +
`깊게 · 중간 · 짧게` 태그로 보여준다. 공은 카드를 열 때 한 번 날아가 **결정하는 순간에 멈추고**, `▶ 다시` 로 다시 본다.

| 대상 | 색 | 모양 | 글자 |
|---|---|---|---|
| **나** | 형광 `#E4FF3D` + 흰 테두리 + 발밑 빛 | 원 | `나` |
| 파트너 | 흰색 | 원 | `짝` |
| 상대 | 남색 `#26357F` | **사각형** | `1` `2` |

색·모양·글자 3중 인코딩으로 색맹 대응. 코트는 **깎은 잔디 줄무늬**, 바깥은 **PANTONE 15-0343 Greenery**.
페이지는 한 가지 밝은 테마로 고정한다 — 다크 모드 기기에서도 밝게 보인다 (v3).
오답 시 **내가 고른 존과 정답 존을 동시에** 보여준다 — "여기가 아니라 여기".
고르면 **결과 장면**이 재생된다 — 내가 뛰고, 공이 이어서 난다(노랑 = 우리 공, 남색 = 상대 공). 끝나면 `✓ 성공` · `△ 아쉬움` · `✕ 실패` 배지와 한 줄.
내 시점에서는 카메라가 나를 따라 움직인다. 재생 중 코트를 누르면 끝 장면으로 건너뛴다.
`prefers-reduced-motion` 이면 움직임 없이 끝 장면만 보여 주고 정보는 전부 남긴다.

> v3 에서 상대를 빨강 → 남색으로 바꿨다. 잔디 위 빨강은 밝기가 잔디와 거의 같아 적록색맹에겐 사라진다.
> 남색은 잔디 대비 3.2:1 (옛 빨강은 파란 코트 대비 2.1:1).

## 7. 기술

| | 선택 | 이유 |
|---|---|---|
| Phase 1 | 웹 (정적 SPA) | 링크 하나로 30명에게 물어본다 |
| Phase 2~ | **Flutter** | 화면이 사실상 전부 코트 그림이다. `CustomPainter` 가 일급 |
| 코트 렌더링 | 직접 그리기 (SVG → CustomPainter) | 좌표계가 이미 정규화돼 있어 이식이 단순 |
| 카드 데이터 | **앱 번들 동봉 + 원격 갱신** | 오프라인 실내 코트 대응. 콘텐츠는 자주 고친다 |
| 백엔드 | 최소 — 진도·구독 상태·미션 응답만 | 1인 개발 범위 |
| 결제 | 스토어 인앱결제 | 전환율 |
| 분석 | 이벤트 로깅 (카드별 정답률 필수) | 난이도 조정의 유일한 근거 |

### 기획서에 빠져 있던 필수 구현 (STEP 7 검수에서 추가)

진도 저장·복원 / **앱 삭제 후 재설치 시 진도** / 구독 복원 버튼(애플 심사 필수) /
카드 데이터 원격 갱신 시 **버전 관리와 마이그레이션**(id가 바뀌면 오답 노트가 깨진다) /
오답 스케줄 시간대 기준(**사용자 로컬 자정**) / 네트워크 없을 때 이벤트 큐잉(실내 코트).

**대안이었던 Expo(React Native)** — Phase 1 웹을 React로 만들었다면 이쪽이 맞다. 현재 웹 프로토타입은 프레임워크 없는 순수 JS라 이식 비용 차이가 크지 않아 Flutter를 택한다.

## 8. 수익화

| 티어 | 가격 | 내용 |
|---|---|---|
| 무료 | 0원 | 1챕터 24장, 하루 5장 |
| 프로 | 월 4,900 / **연 29,000** | 전체 120장, 오답 노트, 10초 룰, 한 포인트, 통계 |
| 코치 | 월 19,000 | 회원 관리, 커리큘럼 배정, 진도 확인 |

**무료·유료 경계를 1챕터에 두는 이유** — 1챕터만으로도 코트에서 달라지는 게 있어야 돈을 낼 마음이 생긴다. 동시에 1챕터는 **위치**만 다루고 **판단**은 안 다룬다. "자리는 알겠는데 공을 어디로 보낼지 모르겠다"가 정확히 결제 지점이다.

**광고는 넣지 않는다.** 문제 푸는 중간 광고는 몰입을 끊고, 학습 앱에서 광고 수익은 구독 대비 비교가 안 된다.

**첫 100명 획득 채널**
1. 동호회 단톡방 (개발자 본인이 속한 곳부터) — 링크 하나
2. 테니스 커뮤니티/카페에 "복식 상황 퀴즈" 형태로 카드 몇 장 공유
3. 레슨 코치 대상 — 무료 코치 계정을 주고 회원에게 권하게 한다

## 13. 이 기획서로 개발을 시작했을 때 2주 안에 막힐 지점 셋

### ① 카드 95장을 누가 언제 쓰는가
파이프라인은 있지만 **속도 추정이 없다.** C1 24장을 쓰는 데 실제로 얼마나 걸렸는지 기록되지 않았다.
8장 배치 하나에 몇 시간인지 재고, 95장의 실제 소요를 Phase 1 일정에 반영해야 한다.
**이 숫자 없이 Phase 2 일정(12주)은 근거가 없다.**

### ② `한 포인트` 분기표를 만들 데이터가 부족하다
`next.id` 는 다음 카드 하나만 가리킨다. 그런데 분기는 **선택마다 다른 다음 카드**가 필요하다.
지금 스키마로는 정답일 때의 다음 수만 있다. **차선·실수를 골랐을 때의 분기가 없다.**
스키마에 `branch: { 정답: id, 차선: id, 실수: id }` 를 추가할지, Phase 3에서 별도 테이블로 뺄지 결정해야 한다.

### ③ 정답률 로깅의 최소 형태가 정의되지 않았다
Phase 1 통과 기준이 "60% 완주"인데, **무엇을 어떻게 기록할지가 없다.** 회원가입이 없으므로 사용자 식별도 없다.
브라우저 로컬 식별자 + 익명 이벤트 전송의 최소 설계를 첫 주에 정해야 한다.
이걸 미루면 Phase 1이 끝나도 **판단할 데이터가 없다.**
