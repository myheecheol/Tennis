# STEP 3 산출물 — 코트 렌더러 명세

> `prompts/03-court-visuals.md` 를 실행한 결과입니다.
> 이 명세는 추측이 아니라 **`web/template.html` 에 실제로 구현된 것**을 옮긴 것입니다.
> 동작하는 구현이 먼저 있고, 문서가 그것을 따라갑니다.

---

## 1. 캔버스와 좌표 변환

세로 화면 기준, 코트를 **세로로 세워** 그립니다. 내가 아래, 상대가 위. 카메라는 절대 뒤집지 않습니다.

```
viewBox : 0 0 400 620
코트 안쪽 : x 40 → 360 (폭 320)  /  y 60 → 560 (길이 500)
네트      : y = 310
```

변환식 — 정규 좌표 `(nx, ny)` → 화면:

```
px(nx) = 40 + nx × 320
py(ny) = 60 + ny × 500
```

**여백을 왜 그만큼 두는가**

| 방향 | 여백 | 이유 |
|---|---|---|
| 위·아래 각 60px | y −0.098 ~ 1.098 | 로브존(`X`)과 베이스라인 뒤로 밀린 마커가 잘리지 않게 |
| 좌·우 각 40px | x −0.15 ~ 1.15 | 사이드라인 밖으로 끌려나간 마커(예: `C1-09` 의 파트너 x=1.04) |

**화면이 좁을 때(360px 폭)** — 코트 SVG는 `width:100%; height:auto` 로 비율을 유지합니다.
버릴 순서는 ① 존 코드 라벨(`E-LX` 등) ② 범례 설명문 ③ 카드 상단 태그.
**마커·라인·경로는 절대 버리지 않습니다.** 그게 문제 그 자체입니다.

## 2. 원근감을 줄 것인가 — **주지 않는다 (완전 평면 탑뷰)**

상대 코트를 사다리꼴로 좁히지 않고, 양쪽을 같은 크기의 직사각형으로 그립니다.

**그렇게 정한 이유 세 가지**

1. **탭 정확도.** 사다리꼴로 좁히면 상대 코트 쪽 존이 화면에서 작아집니다.
   `target` 카드는 정답이 대부분 상대 코트에 있는데, 정답 영역이 가장 작아지는 건 앞뒤가 맞지 않습니다.
2. **존 판정이 단순해진다.** 평면이면 존은 직사각형이고 판정은 부등식 네 개입니다.
   사다리꼴이면 사다리꼴 내부 판정이 되고, 경계 근처 오탭이 늘어납니다.
3. **초보자에게는 거리보다 관계가 중요하다.** 이 앱이 가르치는 건 "얼마나 먼가"가 아니라
   "누가 어디에 있고 나는 어디로 가야 하는가"입니다. 관계는 평면이 더 잘 보여줍니다.

**반대 선택(원근)의 장점** — 실제 코트에서 눈에 보이는 그림과 더 비슷해서, 앱에서 본 장면을
코트에서 떠올리기 쉽습니다. 로브의 깊이감도 살아납니다.
Phase 2에서 **랠리 모드에만** 약한 원근(상대 코트 폭 85%)을 시험해 볼 가치가 있습니다.
학습 모드에는 넣지 않습니다.

## 3. 마커 시스템

색 하나에 기대지 않습니다. **색 + 모양 + 글자**, 세 겹으로 구분합니다.

| 대상 | 모양 | 채움 | 테두리 | 글자 | 반지름 |
|---|---|---|---|---|---|
| **나** | 원 | `--optic` `#E4FF3D` | `--net` 2px | `나` | 12 |
| 파트너 | 원 | `--partner` `#F4F8FA` | `--net` 1.6px | `짝` | 12 |
| 상대 1·2 | **둥근 사각형** | `--brick` `#D9553C` | `--net` 1.6px | `1` `2` | 23×23, r=4 |
| 공 | 작은 원 | `#FFFFFF` | `--net` 1.6px | — | 5.5 |

### "나"를 한눈에 띄게 만드는 장치 — 색 외에 둘

1. **발광 링.** 같은 색의 반지름 18 원을 불투명도 0.2로 뒤에 깝니다.
   그림자가 아니라 링인 이유: 그림자는 코트의 파란 배경에서 탁해 보이고, 링은 형광색이 번져 보입니다.
2. **유일한 난색.** 코트 전체가 파랑 계열이고 상대만 벽돌색입니다. 형광 노랑은 화면에서 나 하나뿐입니다.

크기를 키우는 방법은 **쓰지 않았습니다.** 마커 크기가 다르면 "더 중요한 사람"으로 읽히는데,
복식에서 나와 파트너의 중요도는 같습니다.

### 색맹 대응

적록색맹에게 `#D9553C`(상대)와 `#E4FF3D`(나)는 명도 차이로 구분되지만,
파트너 흰 원과 상대 벽돌색 사각형은 **모양이 다르므로** 색이 사라져도 구분됩니다.
검증 방법: 캡처를 그레이스케일로 변환해 네 마커가 여전히 구분되는지 확인합니다.
(원/원/사각형/사각형 + 글자 `나` `짝` `1` `2` 로 4종이 모두 남습니다.)

## 4. 화면 상태 다섯 가지

| 상태 | 마커 | 지나온 공 | 탭 존 | 정답 존 | 이동 화살표 |
|---|---|---|---|---|---|
| `setup` | ● | ● | ○ | ✕ | ✕ |
| `thinking` | ● | ● | ● (점선 + A/B/C) | ✕ | ✕ |
| `answered-correct` | ● | ● | ✕ | ● (형광 채움) | ● |
| `answered-wrong` | ● | ● | ✕ | ● + **내가 고른 존(빗금)** | ● |
| `replay` | ● | ● | ✕ | ● | ● + 다음 수 |

### 텍스트 와이어프레임 — `thinking`

```
┌──────────────────────────────┐
│              [1]             │  ← 상대 리시버
│  ┌────┬────┬────┐            │
│  │    │    │ [2]│            │  ← 상대 넷맨
│  └────┴────┴────┘            │
│ ●                            │  ← 공 (지나온 경로 끝)
│  ╲                           │
│═══╲══════════════════════════│  ← 네트
│ ┌B╌╌┬╌╌C╌┐                   │  ← 탭 가능한 존 (점선 + 라벨)
│ │(나)│    │                  │
│ ├A╌╌┤                        │
│ └╌╌╌┘                        │
│                    [짝]      │
└──────────────────────────────┘
```

### 텍스트 와이어프레임 — `answered-wrong`

```
│ ┌────┬────┐                  │
│ │▨▨▨▨│████│   ▨ 내가 고른 존 (빗금 + 벽돌색 테두리)
│ │(나)│    │   █ 정답 존 (형광 채움 + 형광 테두리)
│ └────┴────┘                  │
│    ╲                          │
│     ⇢⇢⇢▶  ← 정답으로 가는 노란 점선 화살표
```

**두 존을 동시에 보여주는 게 핵심입니다.** "틀렸다"가 아니라 "여기가 아니라 여기"를 보여줘야
다음에 기억납니다. 오답만 지우고 정답만 보여주면 무엇이 달랐는지 알 수 없습니다.

### 존 라벨(A/B/C)은 존의 **좌상단 모서리**에 둔다

가운데에 두면 선수 마커와 겹칩니다. 실제로 초기 구현에서 겹쳤고, 모서리로 옮겨 해결했습니다.
반투명 흰 원(r=11.5, 20%)을 라벨 뒤에 깔아 코트 라인 위에서도 읽히게 합니다.

## 5. 애니메이션 타임라인

정답을 고른 직후 재생됩니다. **총 1,900ms** — 2.5초를 넘지 않습니다.

| 시각(ms) | 대상 | 동작 | 이징 |
|---|---|---|---|
| 0 | 탭 존 | 사라짐 (opacity 1→0) | `ease-out` 120ms |
| 60 | 정답 존 | 채움 0→22%, 테두리 0→2.5px | `ease-out` 200ms |
| 60 | 내가 고른 존(오답 시) | 빗금 채움 페이드인 | `ease-out` 200ms |
| 260 | 이동/타격 화살표 | `stroke-dashoffset` 로 그려짐 | `ease-in-out` 420ms |
| 680 | 화살촉 | 나타남 | `ease-out` 120ms |
| 800 | 판정 배지 | 아래에서 6px 올라오며 페이드인 | `ease-out` 180ms |
| 980 | 해설 문단 | 페이드인 | `linear` 160ms |
| 1,140 | 한 줄 요약 | 페이드인 | `linear` 160ms |
| 1,900 | — | 끝. 이후 정지 | — |

### 공 경로는 포물선인가

**종류에 따라 다릅니다.** 경로의 수직 이등분선 방향으로 제어점을 띄운 2차 베지어를 씁니다.

| 공 종류 | 띄움(lift) | 이유 |
|---|---|---|
| 발리·낮은 스트로크 | 12px | 거의 직선 |
| 서브·일반 스트로크 | 26px | 기본값 |
| 로브 | 70px | 높이가 곧 정보다 |
| 스매시 | 8px | 내리꽂힘 |

> 현재 구현은 26px 고정입니다. `ball.kind` 로 분기하는 것이 **Phase 1 잔여 작업**입니다.

### `prefers-reduced-motion`

- **끈다**: 화살표 그려지는 애니메이션, 배지 슬라이드, 존 페이드
- **남긴다**: 최종 상태 전부. 정답 존·화살표·해설이 **즉시** 완성된 모습으로 나타납니다
- 움직임을 줄이는 것이지 정보를 줄이는 게 아닙니다

## 6. 탭 판정

- **히트박스는 시각적 존과 같습니다.** 넓히지 않습니다.
  존은 이미 최소 107×70px(실제 기기에서 약 11×7mm)이라 44pt 기준을 넉넉히 넘습니다.
  넓히면 인접 존과 겹쳐서 "분명히 B를 눌렀는데 C가 됐다"가 생깁니다.
- **존 사이 여백 2px** 를 둡니다. 경계를 정확히 누르면 아무 일도 일어나지 않습니다.
  잘못 판정하는 것보다 아무 일도 안 일어나는 게 낫습니다.
- **보기 목록으로도 답할 수 있습니다.** 코트 탭과 아래 버튼이 같은 핸들러를 씁니다.
  손가락이 큰 사용자, 화면이 작은 기기, 스크린리더 사용자 모두를 한 번에 해결합니다.

### 되돌리기는 허용하지 않는다

한 번 고르면 확정입니다. 교육적으로 그게 맞습니다 —
**코트에서는 되돌릴 수 없기 때문입니다.** 다만 `다시 풀기` 버튼으로 카드를 처음부터
다시 시작할 수는 있습니다. 이건 "무르기"가 아니라 "복습"입니다.

## 9. 이 명세로 구현했을 때 가장 망가지기 쉬운 세 곳

### ① 좌우가 뒤집힌다
가장 위험합니다. **실제로 첫 예시 카드에서 일어났습니다** — 서버를 애드 코트에 두고
공은 상대 듀스 박스로 보냈습니다. 사람 눈으로는 그럴듯해 보입니다.

**대비**: `tools/validate_cards.py` 가 기계적으로 막습니다.
서브 출발 x와 착지 x가 센터 0.5 기준 반대편인가, 서브 출발점이 서버 위치와 일치하는가,
서버와 넷맨이 반대 반쪽에 있는가. **카드를 만들 때마다 반드시 돌립니다.**

### ② 마커가 존 라벨을 가린다
존 라벨을 가운데 두면 반드시 겹칩니다. 카드마다 배치가 달라서 눈으로는 다 못 봅니다.

**대비**: 라벨은 좌상단 모서리 고정. 마커 간 최소 거리 0.12를 검증기가 강제합니다.

### ③ 공 경로가 한 점뿐인 카드에서 죽는다
"토스 전" 카드는 공이 아직 안 날아갔으므로 경로가 한 점입니다.
`path[1]` 을 그냥 읽으면 `undefined` 로 터지고, **화면 전체가 비어버립니다.**

**대비**: 경로 길이를 반드시 확인합니다. 한 점이면 화살표 없이 공만,
그것도 서버 마커에 겹치지 않게 네트 쪽으로 0.035 띄웁니다.
(이 버그도 실제로 났고, 카드 데이터를 연결한 첫 빌드에서 화면이 통째로 비었습니다.)
