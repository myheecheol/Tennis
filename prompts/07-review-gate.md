# STEP 7 — 검수 프롬프트 (품질 게이트)

**목적**: 기획서를 **네 사람의 눈**으로 찢어봅니다. 이 단계가 가장 값쌉니다.
**입력**: STEP 6 기획서
**출력**: 지적 목록 + 수정본

---

## 7-A. 4인 페르소나 리뷰

```text
[STEP 6에서 나온 기획서 전문을 여기 붙여넣기]

---

이 기획서를 네 사람이 각각 읽었습니다.
**각자의 이해관계와 말투로**, 이 기획서를 비판하세요.
칭찬은 한 문장까지만. 나머지는 전부 문제 지적입니다.

### ① 테니스 복식 코치 (지도 15년)
전술적 오류만 봅니다.
- 틀린 전술, 조건이 빠진 원칙, 초보에게 위험한 조언을 **카드 번호와 함께** 지적
- "상황에 따라 다른데 하나로 단정한 곳"을 찾아내세요
- 실제 코트에서 안 통할 조언 3가지

### ② 게임 디렉터 (모바일 F2P 10년)
재미와 리텐션만 봅니다.
- 3일 차 이탈 지점이 어디인지
- "의미 있는 선택"이 없는 구간
- 보상 설계에서 비어 있는 곳
- 이 기획서에서 **가장 재미없을 것 같은 모드**를 지목하고 이유

### ③ 1인 개발자 (실제로 만들 사람)
구현 가능성만 봅니다.
- 명세가 모호해서 못 만드는 부분
- 일정이 비현실적인 구간 — **몇 주가 더 필요한지 숫자로**
- 기획서에 없는데 반드시 필요한 것 (에러 처리, 상태 저장, 오프라인 등)
- "이거 하나 때문에 2주 날아갈 것 같은 항목" 1개

### ④ 우리 사용자 (구력 8개월, 40대 직장인)
- 이해 안 되는 용어를 **그대로 인용해서** 지적
- "이건 나한테 안 맞다" 싶은 부분
- 돈을 낼 것인가 — 솔직하게. 안 낸다면 무엇이 있어야 내는가

## 출력
1. 네 사람의 지적을 각각 목록으로
2. 그다음, 네 사람의 지적을 통합해 **심각도 순 문제 목록**을 표로

| # | 문제 | 지적한 사람 | 심각도 | 기획서 어느 절 | 제안 수정 |
|---|---|---|---|---|---|

3. 심각도 `치명`인 항목이 있으면, **그 항목만** 수정한 기획서 절을 다시 써서 첨부
```

## 7-B. 사실 검증 프롬프트

```text
[기획서의 콘텐츠 섹션 + 카드 전문]

이 문서에서 **검증 없이 사실처럼 쓰인 주장**을 전부 찾아내세요.

각각에 대해:
| 주장 | 위치 | 유형 | 확인 방법 |
|---|---|---|---|

유형은 셋 중 하나:
- `전술`: 테니스 전술 주장 → 실제 코치에게 물어야 함
- `시장`: 숫자·규모·경쟁 앱 주장 → 자료 확인 필요
- `사용자`: 사용자가 이렇게 행동할 것이라는 가정 → 테스트 필요

특히 **숫자**를 주의해서 보세요. 지어낸 통계가 있으면 반드시 지적하세요.
마지막으로, 이 중 **출시 전에 반드시 확인해야 할 것 5개**를 우선순위로 뽑으세요.
```

## 7-C. 최종 압축 프롬프트

```text
[수정 완료된 기획서]

이 기획서를 세 가지 길이로 다시 쓰세요. 내용을 빼지 말고 **압축**하세요.

1. **한 문장** — 누군가 "그거 뭐야?"라고 물었을 때의 답
2. **한 단락 (200자)** — 동호회 사람에게 보여줄 소개
3. **한 페이지** — 투자자나 협업자에게 보낼 요약
   (문제 / 해결 / 대상 / 왜 지금 / 어떻게 돈을 버나 / 다음 3개월)

세 가지가 **서로 모순되지 않아야 합니다.**
압축 과정에서 "설명하기 어려운 부분"이 나왔다면, 그건 기획이 덜 된 곳입니다.
어디였는지 마지막에 적으세요.
```

## 검수를 여기서 멈추지 마세요

AI 검수는 **문서 안의 모순**을 잡습니다. **현실과의 모순**은 못 잡습니다.

출시 전에 반드시:
1. **실제 코치 2인에게 카드 20장 감수** — 전술 오류는 이 제품의 신뢰를 통째로 날립니다
2. **동호인 5명에게 종이 카드로 테스트** — 앱을 만들기 전에, 인쇄해서 풀려보세요
   재미없으면 앱으로 만들어도 재미없습니다
